# 🌦️ 날씨 보고 여행지 고르기 (Vue 실습 과제 1 \~ 8)

## 어떤 서비스인가

**"날씨 보고 여행지 고르기"**: 국내 5개 도시(서울·수원·부산·인천·제주)의 실시간 날씨를 한눈에 비교하면서 어디로 떠날지 정하는 걸 도와주는 날씨 대시보드다.

**기획 의도**: 기온만 나열하는 날씨 앱이 아니라, "이번 주말 어디 갈까?"라는 질문에 답하는 데 필요한 정보를 한 화면에 모으고 싶었다. 그래서 도시마다 추천 명소를 달았고, 상세 페이지에는 여행 날짜를 잡는 데 필요한 5일 예보, 야외 활동 가능 여부를 보는 미세먼지 등급, 떠나기 전에 읽어볼 위키백과 도시 소개까지 붙였다.

**주요 기능**:

- **실시간 날씨 비교**: OpenWeatherMap API 기반. 도시별 카드에 큰 날씨 이모지 + 온도(카드에서 가장 크게) + 날씨 상태 + 추천 명소, 최고·최저 기온 도시 표시, 전체 평균 기온
- **도시 검색**: 한글 조합 중에도 즉시 필터링되고, 검색어가 URL(`?q=`)에 동기화돼 새로고침해도 유지됨
- **상세 페이지**: 체감온도·습도·풍속, 5일 예보(정오 기준), 미세먼지 등급 게이지, 위키백과 도시 소개(사진 + 요약)
- **날짜로 여행지 추천**: "이 날짜엔 어디가 좋을까?" 패널에서 날짜를 고르면, 5개 도시의 그 날 예보를 여행하기 좋은 순서(맑음 우선, 쾌적 기온순)로 줄 세워줌: 목적지를 정하기 전에 날씨부터 비교하는 역방향 흐름
- **내 여행 등록**: 목적지+기간(당일치기, 1박 2일, 2박 3일... 2주 뒤도 가능)을 등록하면 홈 맨 위에 D-day가 뜨고, 여행 5일 전부터 일차별 예보가 자동 표시됨. 새로고침해도 유지(localStorage)
- **즐겨찾기**: 카드의 별(☆)로 담고, 즐겨찾기 페이지에서 모아보기 (페이지를 오가도 유지)
- **단위 전환**: 헤더의 ℃/℉ 스위치 하나로 모든 화면의 기온(예보 포함)이 즉시 전환. 한국 여행을 계획하는 화씨권 사용자(미국인 등)를 고려한 기능

## 만든 과정

Vue 3 Composition API(`<script setup>`) 실습 과제.
과제 1(날씨 Mockup) → 과제 2(반응형 시스템 - computed/watch/watchEffect) → 과제 3(컴포넌트 분리 - props/emits/slot) → 과제 4(라우터 적용 - Vue Router) → 과제 5(스토어 적용 - Pinia) → 과제 6(Axios로 실제 API 연동) → 과제 7(외부 UI 라이브러리 - Element Plus 적용) → 과제 8(품질관리·빌드·배포) 순서로 같은 프로젝트에 이어서 구현했다.

- 과제 1\~2는 한 파일(`src/views/WeatherMockup.vue`)에 만들었고, 과제 3부터 views/components/composables/stores 폴더 구조로 쪼갰다. 각 단계 당시의 화면은 `WeatherMockup.vue`(과제 1\~2), `WeatherParent.vue`(과제 3)로 보존해뒀다 (현재 라우터에는 미등록: 최종 앱은 아래 views 5개로 동작).
- 현재 구조: views 5개(`WeatherHomeView`, `WeatherDetailView`, `WeatherAboutView`, `WeatherFavoritesView`, `NotFoundView`) + 레이아웃 컴포넌트(`TheHeader`, `UnitToggler`, `PageHero`) + 기능 패널(`DateComparePanel`, `TripPlanner`) + 재사용 부품(`components/exercise/` 4개) + `composables/`(`useFavorites`, `useWeather`, `useForecasts`, `useDisplayTemp`) + `stores/`(`configStore`, `tripStore`) + `api/`(`weatherApi`, `wikiApi`) + `constants/`(`cities`, `weatherIcons`)
- 과제 8 이후 배포 상태에서 UI/UX 리디자인을 한 차례 진행했다 (아래 "UI/UX 리디자인" 절). **과제 1\~7 절의 화면 묘사는 당시 구현 기준**이라 현재 화면과 다를 수 있다: 로직·요구사항 구현 내용은 그대로고, 바뀐 건 표시 계층(템플릿/스타일)뿐.

```bash

```

실행 후 터미널에 뜨는 주소(`http://localhost:5173`, 포트가 사용 중이면 5174 등으로 바뀜) 접속.

```bash

```

실제 키가 든 `.env`는 `.gitignore`에 등록돼 있어 저장소에 올라가지 않고, 양식인 `.env.example`만 공유된다 (필요한 환경변수가 뭔지 알려주는 설명서 역할).

## 화면 사용법

- **검색**: 검색창에 도시 이름을 입력하면 해당 도시만 필터링된다. 없는 도시를 입력하면 안내 문구가 뜬다. 검색어는 URL 쿼리(`?q=`)에도 반영돼서 새로고침해도 검색 상태가 유지된다.
- **찜하기(즐겨찾기)**: 각 카드 오른쪽의 별(☆)을 누르면 찜 되고(★로 바뀜), 다시 누르면 해제된다. 헤더의 [찜한 여행지]에서 찜한 도시만 모아 볼 수 있다.
- **관광 명소 보기/숨기기**: "지금 여러 여행지 날씨" 제목 오른쪽의 [관광 명소 보기/숨기기] 버튼을 누르면 모든 카드의 추천 명소 줄이 한꺼번에 사라지고, 다시 누르면 나타난다.
- **상세보기**: 카드 안의 [상세보기] 버튼을 누르면 상세 페이지(`/weather/:cityId`)로 이동해 실시간 기온(체감 포함)·습도·풍속에 미세먼지 등급, 5일 예보, 위키백과 도시 소개까지 표시된다. (카드 선택과는 별개로 동작되도록 @click.stop으로 버블링을 차단했다.)
- **단위변경**: 헤더 오른쪽의 ℃/℉ 스위치를 누르면 모든 화면의 기온(예보 포함)이 섭씨 ↔ 화씨로 전환된다.
- **날짜로 비교 · 내 여행**: 히어로 아래 "이 날짜엔 어디가 좋을까?" 제목 오른쪽의 날짜 입력에서 날짜를 고르면 도시들이 여행하기 좋은 순서로 정렬되고(선택 전에는 결과가 뜰 자리에 점선 안내 박스가 미리 표시됨), "내 여행"에 목적지와 기간을 등록하면 D-day 패널이 홈 맨 위로 올라온다. 헤더의 [내 여행] 메뉴를 누르면 어느 페이지에서든 이 섹션으로 바로 이동(스크롤)한다 (자세한 동작은 아래 "직접 추가한 기능" 참고).

## 과제 1 요구사항 구현 위치

1. **배열 렌더링 (v-for)**: `weatherList`를 `ref`로 선언하고 카드 목록을 `v-for`로 출력. key는 index가 아닌 `:key="city.id"`로 바인딩.
2. **조건부 렌더링 (v-if)**: 카드 안에서 `city.temp >= 25`면 🔥 더움 배지, 아니면 `v-else`로 ❄️ 선선함 배지 표시.
3. **:value + @input**: 검색 input에 `v-model` 대신 `:value="searchQuery"` + `@input="onInput"` 조합 사용 (한글 IME 확인 목적). 입력값은 input 아래 "검색 중인 도시: ..."로 실시간 출력.
4. **이벤트 및 수식어**: 카드 클릭 시 `selectCity`로 상태바에 "{도시명}이 선택되었습니다." 표시. [상세보기] 버튼은 `@click.stop="showDetail(...)"`로 alert만 띄우고 카드 클릭 이벤트로 버블링되지 않음. 초기 상태바 문구는 "카드를 클릭하거나 검색해 보세요."
5. **데이터 추가**: 인천(23℃, 흐림 → 선선함 배지), 제주(27℃, 맑음 → 더움 배지) 2개 추가. 25도 기준 라벨이 양쪽 다 나오도록 온도를 나눴다. (과제 2 명세의 값으로 통일)

## 과제 2 요구사항 구현 위치

1. **반응형 상태**: 스크립트 상단에 `searchQuery`, `selectedCityInfo`, `weatherList` 세 개를 `ref`로 선언.
2. **computed 필터링**: `filteredWeatherList`: 검색어가 도시 이름에 `includes`로 포함된 항목만 필터링, 검색어가 비어 있으면 전체 리스트 반환.
3. **watch / watchEffect 구분**:
   - `selectedCityInfo`는 `watch`: 감시 대상이 이 값 하나로 명확하고, 값이 실제로 바뀔 때만 실행되어 첫 로드 때 불필요한 로그가 안 찍힌다. 상태바 문구가 바뀔 때마다 `[watch 감지] ...` 콘솔 출력.
   - `searchQuery`는 `watchEffect`: 콜백 안에서 읽은 반응형 값을 자동으로 의존성 추적하고, 시작 시 1회 즉시 실행된다. 타이핑마다 `[watchEffect 자동 호출] ...` 콘솔 출력.
4. **검색 결과 3분기**: 템플릿에서 `v-if`(검색어 없음 → 원본 전체 리스트) / `v-else-if`(매칭 결과 있음 → 필터링된 리스트) / `v-else`(없음 → "검색 결과가 일치하는 도시가 없습니다" 안내 문구)로 분기.
5. **나만의 상태/computed/watcher**: 컨셉은 "날씨 보고 여행지 고르기". 도시별 추천 명소 2개(`spots`)를 데이터에 추가해 카드와 상세보기 alert에 표시했다.
   - 반응형 상태: `favorites`: 카드의 별(☆/★) 버튼으로 즐겨찾기 토글 (별 버튼도 `@click.stop` 필수: 안 하면 카드 선택까지 같이 눌림), `showSpots`: 명소 보기/숨기기 토글 (정적 데이터인 spots를 반응형 상태로 제어)
   - computed: `hottestId`/`coldestId`: 최고/최저 기온 도시를 찾아 카드에 🔥/🧊 태그로 강조, `avgTemp`(전체 평균 기온), `resultCount`(검색 결과 개수)
   - watcher: `favorites` 변화 시 몇 개 담겼는지 콘솔 출력, `resultCount`를 watch해서 검색 결과가 0개가 되는 순간 콘솔 출력 (computed도 watch 대상이 될 수 있는지 확인해 봄)

## 과제 3 구현 내용 (컴포넌트 분리 - props / emits / slot)

과제 1\~2에서 한 파일이던 화면을 역할별 컴포넌트로 쪼갰다. 페이지 전체는 `views/`, 재사용 부품은 `components/exercise/`, 앱 전체 레이아웃 부품은 `components/` 바로 아래에 두는 기준으로 나눔.

1. **BaseDashboardCard.vue**: 흰색 라운드 패널 디자인을 공통으로 쓰는 래퍼. 본문은 기본 `<slot />`, 타이틀 오른쪽 영역은 `<slot name="header" />`(named slot)로 부모가 주입한다 (홈에서는 명소 토글 버튼, 즐겨찾기에서는 개수 뱃지가 들어감). slot 콘텐츠는 부모 스코프에서 컴파일되므로 부모의 상태/메서드와 직접 바인딩 가능한 점을 활용했다.
2. **SearchBar.vue**: `searchQuery`를 props로 받고 `update-query` 이벤트를 emit하는 프레젠테이션 컴포넌트. 상태 소유는 부모(홈 뷰), 입력 UI만 분리했다. `:value` + `@input` 패턴(한글 IME 실시간 갱신)은 과제 1에서 그대로 가져옴.
3. **WeatherCard.vue**: 도시 하나를 그리는 카드. `city` 객체와 표시 옵션들(`showSpots`, `isFavorite`, `isActive`, `isHottest`, `isColdest`)을 props로 받고, 사용자 동작은 전부 emit(`select-card`, `click-detail`, `toggle-favorite`)으로 부모에 위임한다. 카드가 데이터를 직접 바꾸지 않으니 홈/즐겨찾기 어느 화면에서도 재사용 가능.
4. **StatusBar.vue**: `message` prop 하나만 받는 하단 상태바. 비어 있으면 기본 안내 문구를 자체 표시.
5. **TheHeader.vue**: 공통 타이틀 + 내비게이션 바. 모든 페이지에서 고정이라 App.vue에 직접 두지 않고 레이아웃 컴포넌트로 분리했다.

## 과제 4 구현 내용 (Vue Router 적용)

`src/router/index.js`에 라우트 5개를 등록하고, App.vue의 `<RouterView />` 자리에 현재 URL에 매칭된 뷰가 렌더링되는 구조로 바꿨다. 모든 라우트는 `() => import()` lazy loading: 첫 진입 때 홈만 받고 나머지는 실제로 이동할 때 받는다.

1. **라우트 구성**: `/`(홈 대시보드), `/about`(서비스 소개), `/weather/:cityId`(상세), `/favorites`(즐겨찾기), `/:pathMatch(.*)*`(404)
2. **동적 라우트**: 카드의 [상세보기]가 alert 대신 `router.push('/weather/' + city.id)`로 상세 페이지 이동. 상세 뷰는 `route.params.cityId`로 도시를 찾고, 못 찾으면(주소창에 이상한 id를 직접 친 경우) "데이터 없음" 분기를 보여준다.
3. **검색어 ↔ URL 쿼리 동기화**: 검색어 입력 시 `router.replace`로 `?q=`를 갱신하고(push로 하면 글자마다 뒤로가기 기록이 쌓임), mount 때 1회만 URL → 검색어로 복원한다. 양방향 watch로 묶으면 무한 되먹임이 나서 일부러 단방향 2개로 구성.
4. **내비게이션**: `TheHeader.vue`에서 `<RouterLink>`로 새로고침 없는 화면 전환, `router-link-active` 클래스로 현재 페이지 링크 강조.
5. **404 처리**: 등록 안 된 주소는 전부 `NotFoundView`로 (catch-all `/:pathMatch(.*)*`).
6. **내가 추가한 뷰 + composable**: 즐겨찾기 페이지(`/favorites`)를 추가하면서, 즐겨찾기 상태를 홈 뷰 안에 두면 페이지 이동 시 컴포넌트가 다시 만들어져 리셋되는 문제를 겪었다. → `composables/useFavorites.js`의 모듈 스코프 ref(미니 전역 상태)로 빼서 어떤 뷰에서 쓰든 같은 배열 하나를 바라보게 해결.

## 과제 5 요구사항 구현 위치 (Pinia 스토어 적용)

`npm install pinia`로 설치하고 `src/main.js`에서 `use(createPinia())`로 등록했다.

**왜 하필 "온도 단위" 기능인가**: 이 기능은 과제가 실습 대상으로 지정한 것인데, 전역 상태를 배우기에 딱 맞는 예제라서다: 헤더에서 바꾼 값에 홈 카드·평균 기온·상세 페이지·예보까지 멀리 떨어진 화면들이 전부 반응해야 하니, props 릴레이로는 감당이 안 되고 스토어의 필요성이 몸으로 느껴진다. 서비스 관점의 명분도 있다: 한국 여행을 계획하는 화씨권 사용자에겐 82℉가 28℃보다 직관적이고, configStore는 온도 단위를 시작으로 테마·언어 같은 전역 설정이 앞으로 모일 자리다.

1. **stores/configStore.js 작성**: 날씨 단위를 세팅하는 스토어. 요구사항 표 그대로 구현했다.
   - state: `unit`: 단위를 저장하는 변수 (초기값 `'celsius'`)
   - getters: `unitSymbol`: 현재 단위 상태에 맞는 기호 (℃ / ℉)
   - actions: `toggleUnit`: `'celsius'`와 `'fahrenheit'`를 토글(스위칭)하는 함수
2. **UnitToggler.vue**: 단위 설정을 변경하는 UI 버튼과 영역. "날씨단위: 섭씨(℃)" 문구 + [단위변경] 버튼으로 구성했고, 앱 전체 부품이라 `src/components/` 바로 아래에 뒀다. state/getter를 구조분해할 때 `storeToRefs`를 써야 반응성이 안 끊긴다는 걸 여기서 적용했다 (action은 그냥 함수라 바로 꺼내도 됨).
3. **Navigation Bar 옆에 배치**: `TheHeader.vue`에서 내비 바와 UnitToggler를 `.top-bar` flex 한 줄로 나란히 배치 (mockup처럼 내비 왼쪽 / 단위 오른쪽).
4. **메인과 상세 날씨에 단위 설정 변경 적용**: 기본 원본 데이터(`temp`)는 섭씨 숫자 그대로 두고, 화면에 뿌릴 값만 `displayTemp` computed로 변환했다. 적용 위치: `WeatherCard.vue`(메인·즐겨찾기 공용 카드), `WeatherDetailView.vue`(실시간 기온), 홈의 전체 평균 기온. 단위 기호도 하드코딩(℃) 대신 스토어의 `unitSymbol`을 바인딩해서 [단위변경]을 누르면 전 화면이 즉시 갱신된다.
   - (참고) 과제 슬라이드의 "메인/상세에 적용하면 유사한 코드가 중복됨 → Composable로 해결 가능함 (범위 제외)" 부분을 범위 밖이지만 실제로 구현했다. 화씨 변환 공식(`Math.round(temp * 9 / 5 + 32)`)은 스토어의 `convert` 함수형 getter 한 곳에만 두고, "변환값 + 단위 기호"로 조립해 표시하는 부분은 `composables/useDisplayTemp.js`의 `formatTemp`로 모았다. 덕분에 카드/상세/예보 테이블이 전부 `{{ formatTemp(temp) }}` 한 줄로 통일됨 (computed가 아니라 함수로 만든 이유: 예보 테이블처럼 행마다 다른 값을 넘기는 자리에서도 쓰기 위해).
5. **본인만의 state/getter/action 추가**: 별도 스토어 대신 configStore에 추가하는 방식을 택했다.
   - state: `toggleCount`: 단위를 몇 번 변경했는지 세는 카운터. UnitToggler에 "N회 변경" 뱃지로 표시해서(한 번도 안 눌렀으면 숨김) 스토어 상태 변화가 UI에 실시간 반영되는 걸 확인하는 용도. 새로고침하면 0으로 초기화된다.
   - getter: `unitLabel`: 현재 단위의 한글 이름('섭씨'/'화씨'). `unitSymbol`과 조합해 헤더의 "날씨단위: 섭씨(℃)" 문구를 만든다.
   - getter: `convert`: 섭씨 원본값 → 현재 단위 변환값을 돌려주는 함수형 getter (위 4번에서 설명한 중복 제거의 핵심).
   - action: `setUnit(unit)`: 토글이 아니라 특정 단위로 직접 지정하는 액션. `'celsius'`/`'fahrenheit'` 외의 값은 무시하는 방어 로직을 넣었다. 현재 UI에서 호출하는 곳은 없는 예비용 API.

## 과제 6 요구사항 구현 위치 (Axios로 실제 API 연동)

`npm install axios`로 설치했다. API 호출 코드는 전부 `src/api/` 폴더에 모아서, 컴포넌트에는 URL도 키도 안 보이게 했다.

1. **OpenWeatherMap API로 실제 날씨 데이터 적용**: `api/weatherApi.js`에 axios 인스턴스를 만들어 baseURL + 공통 파라미터(`appid`(키), `units=metric`(섭씨), `lang=kr`)를 한 번만 장착했다. 키는 `.env`의 `VITE_WEATHER_API_KEY`를 `import.meta.env`로 읽는다.
   - 홈/즐겨찾기의 하드코딩 mock을 삭제하고 `composables/useWeather.js`로 교체: `useFavorites`와 같은 모듈 스코프 ref 패턴이라 두 페이지가 같은 목록을 공유하고, 한 번 받아오면 페이지를 오가도 재호출하지 않는다(무료 호출량 절약). 5개 도시는 `Promise.all`로 병렬 호출.
   - 도시별 고정 정보(이름/좌표/명소)는 `constants/cities.js`로 분리: 홈/즐겨찾기/상세에 3중복이던 mock이 상수 하나로 정리됐다.
   - OWM의 날씨 대분류(Clear/Clouds/Rain...)를 기존 한글 상태('맑음'/'구름'/'비'/'흐림'/'눈')로 번역하는 `toStatus` 매핑을 뒀다. 덕분에 이모지·배지·검색·즐겨찾기·단위변환 화면 로직은 무수정으로 동작. ('눈'과 ❄️ 이모지는 실제 API를 붙이면서 새로 생긴 케이스라 추가)
   - **로딩/실패/성공 3분기 UI 추가**: 비동기 호출이라 "응답 오기 전 화면"이 반드시 존재한다. 로딩 문구, 실패 시 [다시 시도] 버튼(강제 재호출), 빈 배열일 때 `reduce`/평균 계산이 터지지 않게 가드도 넣었다.
2. **OWM 추가 API로 기능 확장**: 상세 페이지에 두 가지를 추가했다.
   - **5 Day / 3 Hour Forecast API**: 3시간 간격 40개 응답에서 "매일 정오" 항목만 추려(`new Date(dt*1000).getHours() === 12`) 하루 한 줄짜리 5일 예보로 표시. 예보 기온도 configStore의 `convert`를 그대로 써서 단위변경이 즉시 반영된다.
   - **Air Pollution API**: 대기질 지수(aqi 1\~5)를 한글 등급(좋음\~위험)과 색깔 뱃지로, 초미세먼지/미세먼지 수치와 함께 표시.
   - 현재날씨+예보+미세먼지 3종은 `Promise.all`로 병렬 호출: 순서대로 기다리면 3배로 느려진다.
   - (설계 결정) 이 3종을 한 번에 주는 One Call API도 있지만, 별도 유료 구독(One Call by Call, 무료 티어도 카드 등록 필요)이 필요해서 쓰지 않았다. 무료 API 3번 병렬 호출로 같은 데이터를 받을 수 있고 속도도 문제없어서, 구독 없이 가는 쪽을 택했다. Postman으로 직접 테스트해보면 One Call은 401(구독 필요), 2.5 계열은 200이 돌아온다.
3. **기타 외부 API로 기능 확장: 위키백과 요약 API** (`api/wikiApi.js`): 상세 페이지 하단에 도시 소개 문단 + 대표 사진 + 원문 링크("여행 전에 알아두기")를 표시. 이 API를 고른 이유: 가입/키 발급이 필요 없고, CORS가 열려 있어 브라우저에서 바로 호출되고, 프로젝트 컨셉(날씨 보고 여행지 고르기)과 맞는다. 부가 정보라서 **호출 실패해도 날씨 화면은 살도록 try/catch를 날씨와 분리**했다: 실패하면 소개 카드만 조용히 숨는다.

**직접 발견한 문제: 제주 소개 문구가 "제주특벨ㅈ · 치도"처럼 오타로 깨져 보임**

- **원인 파악**: 위키백과 응답 원문을 문자 단위(유니코드)로 뜯어보니 오타가 아니었다. 그 부분은 제주어(제주 방언) 표기 "제주특벨ᄌᆞ치도"인데, 여기 쓰인 `ᆞ`가 현대 한글에서 사라진 옛 모음 **아래아(ㆍ)**다 (제주어에는 이 모음이 살아 있어서 위키백과가 옛한글 자모로 정확히 적어둔 것). 문제는 일반 폰트가 옛한글 자모(초성 ᄌ + 중성 ᆞ)를 한 글자로 조합하지 못해서, 브라우저가 낱자를 따로따로 그리며 깨진 오타처럼 보인 것. 즉 데이터도 맞고 코드 버그도 아니고, 순전히 **폰트의 옛한글 미지원** 문제였다.
- **해결 방법 비교**: ① 옛한글 지원 폰트를 추가하는 방법은 사용자 컴퓨터에 폰트가 없으면 여전히 깨지고, 웹폰트로 넣자니 괄호 병기 한 줄 때문에 수 MB를 로딩해야 해서 배보다 배꼽이 크다. ② 요약 첫머리의 괄호 병기(한자·방언·영어 표기)를 잘라내는 방법은 깨짐을 원천 차단하고, 여행 소개 카드에 사전식 병기는 어차피 군더더기라 문장도 "제주특별자치도는 대한민국의…"으로 시작해 오히려 읽기 좋아진다. → ②를 선택.
- **구현**: `wikiApi.js`의 `stripLeadingParen` 이라는 함수. 문서 제목 바로 뒤에 붙은 괄호 한 덩어리만 제거한다(첫 공백보다 뒤에 나오는 문장 중간 괄호는 안 건드림). 병기 안에 중첩 괄호가 있을 수 있어서 단순 정규식 대신 여닫이 개수를 세며 짝이 맞는 지점을 찾고, 짝이 안 맞으면 자르지 않고 원문을 그대로 둔다. API 응답을 우리 형식으로 다듬는 번역 계층(api 폴더)에 넣어서 컴포넌트는 이 문제를 몰라도 된다.

**과제 6에서 배운 주의점**: 프론트엔드의 `.env`는 "비밀"이 아니다. `VITE_` 접두사 변수는 빌드 결과물(JS)에 그대로 박혀서 브라우저에서 다 보인다. `.env`를 gitignore하는 건 "저장소에 안 올리는 것"일 뿐이고, 진짜 숨겨야 하는 키라면 백엔드 서버를 거쳐야 한다. (이번 키는 무료 플랜이라 이 구조로 충분)

## 과제 7 구현 내용 (외부 UI 라이브러리 - Element Plus)

`npm install element-plus`로 설치하고, main.js에서 `use(ElementPlus)` + CSS import로 전역 등록했다 (전역 등록이라 컴포넌트마다 import 없이 `<el-button>` 같은 태그를 바로 씀).

**라이브러리 선정 이유 (Element Plus)**: 후보(PrimeVue, Vuetify, Ant Design Vue, Quasar, Naive UI) 중에서 골랐다. ① Element Plus의 주력 용도가 관리자 페이지·대시보드인데 이 앱이 정확히 날씨 대시보드라 결이 맞고, ② 우리 앱에 필요한 부품(입력창, 카드, 태그, 스켈레톤, 빈 상태, 설명 리스트)이 전부 있어서 "직접 만든 것 → 라이브러리 것" 1:1 교체가 가능하며, ③ CSS 변수 기반 테마라 주 색상만 바꿔서 기존 인디고/파스텔 디자인을 유지할 수 있고(Vuetify는 Material 스타일 강제가 셈), ④ 국내 사용층이 두터워 한국어 자료 찾기도 쉽다.

**적용 원칙: 로직은 무수정, UI 계층만 교체**: 과제 3\~6에서 화면과 로직(stores/composables/api)을 분리해둔 덕분에, 이번 과제에서 스토어·composable·api 폴더는 한 줄도 안 바꾸고 템플릿의 마크업만 갈아끼웠다. 관심사 분리가 잘 돼 있으면 UI 교체 비용이 싸진다는 걸 체감한 과제.

화면별 교체 내역:

- **테마 커스터마이징** (App.vue 전역 스타일): Element Plus는 색을 전부 CSS 변수로 쓰기 때문에 `:root`에서 `--el-color-primary`를 우리 인디고(#4f46e5)로 덮고 light-3\~9 단계, 폰트, el-card 모서리(16px)까지 기존 디자인에 맞췄다.
- **BaseDashboardCard**: 직접 만든 흰 패널 div → `el-card`. 우리 slot 구조(#header/기본)를 el-card의 slot에 그대로 이어붙이는 얇은 래퍼가 됐다. 이걸 쓰는 홈/즐겨찾기는 자동으로 적용받음.
- **SearchBar**: 직접 만든 input → `el-input`(돋보기 prefix + clearable 지우기 버튼이 공짜로 생김). 한글 IME 즉시 동기화를 위해 `v-model` 대신 `:model-value` + `@input` 조합은 그대로 유지. 다만 과제 1의 학습 확인용 흔적이던 패널 제목의 "(한글 즉시 동기화)" 라벨과 "검색 중인 도시: ..." 표시 줄은 완성된 앱답게 정리함: 동작(조합 중 글자까지 실시간 필터링)은 그대로고, 그 시절 원본 화면은 WeatherMockup.vue에 보존돼 있다.
- **WeatherCard**: 더움/선선함·최고/최저기온 배지 → `el-tag`(type으로 색 구분), [상세보기] → `el-button`. 카드 틀과 별(☆) 버튼은 선택 강조(active border)·호버 애니메이션 같은 커스텀 동작이 있어서 직접 만든 걸 유지: 전부 바꾸는 게 목적이 아니라 맞는 부품만 골라 쓰는 게 목적.
- **UnitToggler**: [단위변경] 버튼 → `el-switch`(℃/℉ 양쪽 라벨). 스위치 on/off는 스토어 unit에서 계산하고 change 때 기존 `toggleUnit` 액션을 그대로 호출. 변경 횟수 뱃지는 `el-tag`.
- **홈 뷰**: 로딩 문구 → `el-skeleton`(회색 뼈대가 깜빡이는 진짜 로딩 UI), 에러 → `el-alert` + 다시 시도 `el-button`, 검색 결과 없음 → `el-empty`(일러스트 포함), 명소 토글 → `el-button`.
- **상세 뷰**: 기온/습도/풍속 목록 → `el-descriptions`(라벨-값 표), 5일 예보 → `el-table`(기온 열은 슬롯에서 `formatTemp` 호출이라 단위변경 즉시 반영), 미세먼지 → `el-tag` + `el-progress` 게이지(aqi 1\~5 → 20\~100%, 등급별 색), 위키 사진 → `el-image`(클릭하면 크게 보기 preview가 공짜), 없는 도시 → `el-empty`.
- **즐겨찾기 뷰**: 개수 뱃지 → `el-tag`, 빈 상태 → `el-empty` + 이동 버튼.
- **404(NotFound)**: `el-result`(결과 안내 전용 컴포넌트) + `el-button`.
- **반응형 레이아웃**: 과제 1부터 내려온 480px 단일 컬럼은 모바일에선 좋았지만 데스크톱에선 좌우 여백이 과했다. Element Plus의 레이아웃 시스템 `el-row`/`el-col`로 홈·즐겨찾기의 카드 목록을 그리드화: 한 줄 24칸 기준으로 `:md="12"`(데스크톱 2열) / `:xs="24"`(모바일 1열)를 지정하면 media query 없이 화면 폭에 따라 자동 전환된다. 컨테이너 폭은 카드 목록 페이지 960px, 세로로 읽는 페이지(상세/소개/404)는 560px로 조정.

**트레이드오프 기록**: 전역 등록은 안 쓰는 컴포넌트까지 번들에 들어가서 빌드 결과가 약 100kB → 1MB(gzip 346kB)로 커졌다. 실무에서는 unplugin-vue-components로 쓰는 것만 자동 import해서 해결하는데, 수업 규모에선 코드가 단순한 전역 등록을 택하고 이 트레이드오프를 인지만 해뒀다.

## 직접 추가한 기능 (과제 외: 기획 의도 살리기)

과제를 다 만들고 나서 "이 앱이 정말 그 불편(목적지 정하고 날씨를 매번 또 찾아보는 귀찮음)을 해결하나?"를 다시 봤더니, 여전히 사용자가 도시를 먼저 고르고 예보를 찾아 들어가야 했다. 그래서 두 기능을 추가로 만들었다. 무료 API 예보가 5일까지라는 제약을 기능 설계로 감싼 게 포인트.

1. **날짜 기준 도시 비교** (`components/DateComparePanel.vue`): 흐름을 뒤집어서 날짜를 먼저 고르게 했다. `el-date-picker`로 날짜를 고르면(예보 범위 밖 날짜는 `disabled-date`로 달력에서 비활성화) 5개 도시의 그 날짜 예보를 "여행하기 좋은 순서"로 정렬해 보여준다: 1순위 날씨 좋음(맑음 > 구름 > 흐림 > 눈 > 비), 동순위면 걷기 좋은 기온(24℃)에 가까운 순. 1위엔 "여기 어때요?" 태그가 붙는다. 예보 5도시분은 무거워서 미리 안 받고 날짜를 고르는 순간에 받는다(`composables/useForecasts.js`에 모듈 스코프 캐시).
2. **내 여행 등록** (`components/TripPlanner.vue` + `stores/tripStore.js`): "제주, 9월 10일\~12일"처럼 목적지+기간을 등록하면 홈 맨 위에 D-day 카드("제주 2박 3일 여행 D-14")가 뜨고, 여행 날짜들이 예보 범위(5일 전) 안에 들어오는 순간부터 일차별 예보가 자동으로 나타난다. 기간 선택은 `el-date-picker`의 daterange 모드(당일치기는 같은 날을 두 번 클릭). 2박 3일이면 첫날만 범위에 들어온 상태도 있어서 날짜별로 "예보 / 예보 대기"를 하루씩 판정한다. 시작일이 지났는데 종료일이 안 지난 "여행 중" 상태도 라벨로 구분. 2주 뒤 여행도 등록 가능: 그때까진 D-day만 세다가 때가 되면 예보가 뜨는 구조라, "예보는 5일까지"라는 API 제약이 사용자에겐 "앱이 알아서 챙겨준다"는 경험으로 바뀐다.
   - `tripStore`는 과제 5 요구사항 4의 "본인만의 추가 Store를 작성하고 활용" 케이스이기도 하다. configStore(앱 설정)와 성격이 달라서(사용자 데이터) 스토어를 분리했고, 새로고침에도 남도록 localStorage에 저장했다가 스토어 초기값으로 읽어온다.
3. **공통 기반** (`composables/useForecasts.js`): 두 패널이 같은 예보 캐시를 공유한다. 도시×날짜로 예보 한 줄을 뽑는 `getDayForecast`(정오 우선, 정오가 지난 오늘은 남은 시간대로 대체)도 여기에 있다.
4. **화면 구성·문구를 기획 의도에 맞게 정리**: 기능을 다 만들고 보니 화면 순서와 이름이 "날씨 앱" 시절 그대로라 서비스 정체성이 안 읽혔다.
   - **홈 순서**: 사용자 여정(날짜 고르기 → 여행지 비교 → 찜/등록 → D-day 추적)대로 재배치. 부제가 가리키는 날짜 비교 패널을 맨 위로, 검색은 현황 목록을 거르는 도구라 현황 카드 안으로 합침. **내 여행 패널은 조건부 배치**: 등록 전엔 여정의 마지막 단계라 맨 아래(폼), 등록 후엔 D-day 카드가 첫눈에 보이게 맨 위로 올라온다.
   - **이름을 "여행" 언어로 통일**: 내비 [날씨 대시보드]→[여행지 고르기], [즐겨찾기]→[찜한 여행지], 현황 패널 제목 [지역별 날씨 현황]→[지금 여러 여행지 날씨], 검색 placeholder [도시]→[여행지]. 별(☆) 버튼엔 `el-tooltip`으로 "여행지 찜하기" 설명 추가.
   - **서비스 소개 페이지 개편**: 기술 설명("Vue 3 기반 실습용...")뿐이던 페이지를 "왜 만들었나(기획 스토리) → 이렇게 쓰세요(`el-steps` 3단계 사용 흐름) → 기술 스택 한 줄"로 재구성: 기획 의도가 README뿐 아니라 앱 안에서도 읽히게.

(다음 확장 아이디어: 가입·키가 필요 없는 Open-Meteo API는 16일 예보를 무료로 줘서, 이걸 붙이면 "2주 뒤" 날짜도 등록 즉시 예보를 보여줄 수 있다. 10일 이후 예보는 정확도가 낮아 참고용 표시가 필요.)

## 과제 8 구현 내용 (Source Code 품질관리 · Build & Deployment)

**1. ESLint 점검**: `eslint` + `eslint-plugin-vue`를 설치하고 `eslint.config.js`(flat config)에 JS 기본 규칙(`js.configs.recommended`) + Vue 3 필수 규칙(`flat/essential`)을 설정했다. `npm run lint`로 실행. 첫 점검에서 에러 4건이 나왔는데 전부 `catch (e)`에서 `e`를 안 쓴다는 no-unused-vars였다: 최신 ESLint는 catch 매개변수까지 미사용 검사를 한다. 에러 객체가 필요 없는 자리들이라 `catch { }`(optional catch binding) 문법으로 고쳐 **0 errors** 확인.

**2. API 키 관리**: 과제 6 때부터 해둔 구조 그대로: 키는 `.env`의 `VITE_WEATHER_API_KEY`로 분리, `.gitignore`에 등록돼 Git에 안 올라가고, 채점자/팀원용 양식은 `.env.example`로 공유 (위 "실행 방법" 참고). git 저장소를 만들면서 `git ls-files`로 `.env`가 실제로 추적 안 되는 것까지 확인했다.

**3. Build**: `npm run build`로 `dist/`에 정적 파일 생성, 에러 없이 통과.

**4. Vercel 배포 (GitHub 리모트 기반)**: git 저장소를 GitHub에 올리고, Vercel이 저장소를 가져와 자동 빌드·배포하도록 연결했다. 이때 미리 챙겨야 했던 것 두 가지:

- **환경변수 등록**: `.env`는 Git에 없으니 Vercel이 빌드할 때 키를 모른다 → Vercel 프로젝트 설정의 Environment Variables에 `VITE_WEATHER_API_KEY`를 따로 등록해야 배포된 사이트에서 날씨가 뜬다.
- **SPA 새로고침 404 대비**: history 모드 라우터라 `/weather/city_01` 같은 주소를 직접 열면 서버엔 그런 파일이 없어 404가 난다 → `vercel.json`의 rewrite 설정으로 모든 경로를 `index.html`로 돌려보내 라우터가 처리하게 했다.

## UI/UX 리디자인 (과제 8 이후: 배포 상태에서 개선)

배포까지 마친 뒤, "금융 서비스 랜딩페이지처럼 깔끔한 톤"을 목표로 UI를 전면 리디자인했다. **원칙은 과제 7과 동일: 기능/로직/스토어/라우팅은 무수정, 템플릿과 스타일만 교체.** 관심사 분리 덕에 이번에도 stores/composables/api는 거의 그대로였다(표시용 데이터 필드 추가 정도).

**1. 디자인 시스템 정리**

- 배경: 보라/핑크 그라데이션 전면 배경 → 연회색(#F7F8FA) 단색. 포인트 컬러는 인디고(#4f46e5) 1가지로 제한.
- 텍스트 색상 토큰 3단계를 전역 CSS 변수로 정의(`--color-heading` #111827 / `--color-text` #1f2937 / `--color-text-sub` #4b5563)하고, Element Plus 텍스트 변수도 같은 값으로 덮어 표(descriptions/table) 내부까지 통일.
- 타이포 위계: 섹션 제목 27px / 도시명 22px / **온도 42px(카드에서 가장 크게)** / 본문 15\~16px / 캡션 13\~14px. 버튼·입력은 radius 8px로 전역 통일, hover 시 1px 상승 + 그림자(0.2s).
- 카드는 "1px 연회색 테두리" 한 가지만(상시 그림자 제거, hover 때만 은은하게).

**2. 레이아웃 재구성**

- 상단에 sticky 헤더 신설: 좌측 워드마크, 우측 내비([여행지 고르기]·[찜한 여행지]·[내 여행]·[서비스 소개]) + ℃/℉ 토글. [내 여행]은 별도 라우트 없이 홈의 해당 섹션으로 스크롤 진입(라우터 무수정).
- 본문은 max-width 1140px 중앙 컨테이너, 도시 카드는 데스크톱 3열 / 태블릿 2열 / 모바일 1열 그리드(`el-col :xs="24" :sm="12" :md="8"`).
- "카드 속 카드" 중첩 해소: 섹션 래퍼(`BaseDashboardCard`)를 el-card에서 "배경 위 헤딩 + 콘텐츠" 섹션으로 바꿔 바깥 컨테이너 카드를 제거. 섹션 제목엔 4px 인디고 accent bar를 달았다 (이후 아래 "후속 다듬기"에서 제거).
- 페이지 상단에 full-width 파스텔 그라데이션 히어로(`PageHero.vue`): 홈은 큰 버전(가치 제안 문구), 상세/찜/소개는 페이지 제목이 들어간 compact 버전으로 전 페이지 톤 통일.
- 핵심 기능인 날짜 선택 입력을 섹션 제목 아래 큰 필드(높이 54px, 글자 17px)로 승격 (이후 아래 "후속 다듬기"에서 제목 줄 오른쪽으로 이동).

**3. 장식 요소 정리**

- 장식 이모지(제목·메뉴·버튼의 📅🗺️⭐📍 등) 전면 제거: 필요한 자리(검색 돋보기, 위치 핀)는 회색 SVG 라인 아이콘으로 대체. 날씨 이모지는 도시 카드의 큰 이모지와 상세 페이지(현재 날씨 56px + 5일 예보 행 19px)에만 사용하고, 매핑을 `constants/weatherIcons.js` 하나로 공유.
- 알약(pill) 배지 정리: 최고/최저기온·D-day·찜 개수·대기질 등의 `el-tag`를 일반 텍스트로 바꾸고, "더움/선선함(25도 기준)" 배지는 정보가치가 낮아 완전히 삭제(과제 1 당시 화면은 `WeatherMockup.vue`에 보존).

**4. "온흐림" 표기 수정**: OWM이 `lang=kr`로 주는 날씨 설명에 "온흐림"(overcast clouds) 같은 어색한 번역이 섞여 있어, API의 description을 그대로 출력하지 않고 `weather[0].id` 코드 기준 한국어 매핑(`toKoDescription`: 800 맑음, 801\~802 구름 조금, 803 구름 많음, 804 흐림, 5xx 비, 6xx 눈, 2xx 뇌우 등)을 만들어 카드·상세·예보에 일괄 적용했다. 정렬·이모지·검색이 쓰는 대분류 `status`는 그대로 둬서 로직 무수정.

**5. 후속 다듬기 (제출 전 마무리)**: 리디자인 후 화면을 다시 보며 세 가지를 더 다듬었다. 원칙은 동일: 기능/로직 무수정, 템플릿·스타일만 수정.

- **섹션 제목의 accent bar 제거**: 홈 섹션 제목과 상세/소개 페이지 소제목에 붙였던 4px 인디고 세로 바를 전부 제거했다. 포인트 컬러 사용처를 줄이고, 제목은 타이포 위계(크기 27px·굵기 700)만으로 세우는 쪽이 더 깔끔해서다.
- **"이 날짜엔 어디가 좋을까?" 레이아웃 변경**: 날짜 선택 입력을 섹션 제목과 같은 줄 오른쪽 끝으로 옮겼다 (`BaseDashboardCard`의 header slot 활용, 54px 크기는 유지). 그리고 결과 영역을 상시 노출로 바꿨다: 날짜를 고르기 전에도 점선 보더의 empty state 박스("날짜를 선택하면 이곳에 5개 도시가 여행하기 좋은 순서로 표시돼요")가 결과가 뜰 자리를 미리 보여주고, 실제 결과 카드와 같은 최소 높이(150px)를 잡아 선택 전후 레이아웃이 튀지 않게 했다. 기존에 입력 필드 아래 따로 있던 안내 문구는 empty state 문구로 통합.
- **"내 여행" empty state**: 같은 원리로 등록 폼 아래에 점선 보더 empty state("여행지와 기간을 등록하면 여행 5일 전부터 이곳에 일차별 예보가 표시돼요")를 추가하고, 폼 아래 설명 문구를 여기로 흡수했다. 두 섹션의 empty state는 같은 스타일(점선 보더·연회색 배경·같은 문구 톤)로 통일해서 "여기에 결과가 뜬다"는 패턴이 일관되게 읽히도록 했다.

## 트러블 슈팅 기록

과제를 진행하며 실제로 만난 문제들과 푼 과정. 자세한 내용은 각 과제 절에 있고, 여기선 "증상 → 원인 → 해결"만 모았다.

1. **페이지를 갔다 오면 즐겨찾기가 리셋됨** (과제 4): 상태를 홈 뷰 안에 둬서, 페이지 이동으로 컴포넌트가 다시 만들어질 때 같이 초기화된 것 → 모듈 스코프 ref(composable)로 컴포넌트 밖에 승격해 해결. 이 경험이 과제 5에서 Pinia의 필요성을 이해하는 밑거름이 됐다.
2. **검색어 ↔ URL 동기화 무한 되먹임 위험** (과제 4): 양방향 watch로 묶으면 검색어→URL→watch→검색어 루프 → 단방향 두 개(입력 시 `router.replace`, mount 때 1회만 URL→검색어 복원)로 분리해서 원천 차단.
3. **새로 발급한 API 키가 One Call에서 401** (과제 6): "Invalid API key"라는 메시지만 보면 키 문제 같지만, 같은 키가 `2.5/weather`에선 200이었다 → 키가 아니라 플랜 권한 문제(One Call은 별도 구독, 신규 계정엔 미개방)로 판별 → 무료 엔드포인트 3개(현재날씨/예보/대기질)를 `Promise.all` 병렬 호출로 대체. **에러 메시지를 그대로 믿지 말고 교차 검증**할 것.
4. **실제 API 전환 후 빈 데이터 렌더링 에러 가능성** (과제 6): mock 시절엔 데이터가 항상 있었지만 응답 전엔 빈 배열 → 초기값 없는 `reduce`는 예외를 던지고 평균은 0으로 나누기가 됨 → `length` 가드 + 로딩/실패/성공 3분기 UI로 해결.
5. **제주 소개 문구가 "제주특벨ㅈ·치도"처럼 깨져 보임** (과제 6): 원인 후보를 데이터/코드/렌더링 세 층으로 나누고 응답 원문을 유니코드 단위로 확인 → 데이터는 정상(제주어 표기의 옛한글 아래아 ᆞ), 일반 폰트가 옛한글 조합을 못 그리는 **렌더링 문제**로 판별 → 폰트 추가(사용자 환경 의존 + 용량) 대신 괄호 병기를 잘라내는 `stripLeadingParen`으로 원천 차단. 병기 안에 중첩 괄호가 있어 정규식 대신 여닫이 개수 세기로 구현.
6. **새로고침하면 여행 계획이 사라짐** (자체 기능): 스토어는 메모리라 새로고침(JS 전체 재실행)에 초기화됨 → localStorage에 저장하고 스토어 초기값으로 읽어오는 구조로 해결. "페이지 이동에 살아남는 것(스토어)"과 "새로고침에 살아남는 것(localStorage)"은 다른 문제라는 걸 배움.
7. **ESLint 첫 점검 에러 4건** (과제 8): 위 과제 8 절 참고. `catch (e)` 미사용 매개변수 → optional catch binding.
8. **배포에서 터질 문제 선제 처리** (과제 8): SPA 새로고침 404와 Vercel 빌드 시 키 부재. 로컬에선 재현이 안 되고 배포해야 드러나는 유형이라 미리 `vercel.json`과 환경변수 등록으로 대비.
9. **날씨 설명이 "온흐림"으로 표시됨** (리디자인): OWM `lang=kr` 응답의 어색한 기계 번역이 원인 → API 문구를 그대로 출력하지 않고 `weather[0].id` 코드 기준 자체 한국어 매핑(`toKoDescription`)으로 교체. 외부 API의 표시용 문자열은 신뢰하지 말고 코드값 기준으로 직접 매핑할 것.
10. **full-width 히어로를 넣자 가로 스크롤이 생김** (리디자인): 중앙 컨테이너 안에서 `width: 100vw`로 탈출시키면 스크롤바 폭만큼 가로가 넘침 → `body`에 `overflow-x: clip`으로 해결. `hidden`을 쓰면 스크롤 컨테이너가 새로 생겨 sticky 헤더가 깨지므로(`position: sticky`의 기준이 바뀜) `clip`이어야 한다.

## 배우며 느낀 점

- **관심사 분리는 미래의 나를 위한 보험이었다.** 과제 7에서 UI 라이브러리로 화면을 통째로 갈아탈 때 stores/composables/api 폴더는 한 줄도 안 고쳤다. 과제 3\~6 내내 "로직은 밖으로, 화면은 템플릿에"를 지킨 덕인데, 왜 나누는지를 머리로만 알다가 교체 비용이 확 줄어드는 걸로 체감했다.
- **제약은 없애는 게 아니라 설계로 감싼다.** 무료 예보가 5일까지라 "2주 뒤 날씨"는 못 보여준다. 그런데 "여행을 등록해두면 5일 전부터 자동으로 보여준다"로 흐름을 뒤집으니, 같은 제약이 사용자에겐 "앱이 알아서 챙겨준다"는 경험이 됐다.
- **보이는 것 말고 데이터를 확인한다.** 옛한글 깨짐 사건에서, 눈에는 오타로 보여도 유니코드를 까보니 정상 데이터였다. 텍스트가 이상하면 "보이는 모양"이 아니라 실제 코드값을 봐야 한다.
- **에러 메시지는 단서지 결론이 아니다.** "Invalid API key"의 실제 원인은 플랜 권한이었다. 같은 키로 다른 엔드포인트를 호출해보는 교차 검증으로 원인을 갈랐다.
- **AI와 협업하며 공부한 방식**: 코드는 AI와 함께 작성했지만, 각 단계에서 이해한 개념과 원리는 [공부노트.md](./공부노트.md)에 25개 섹션으로 직접 정리하며 따라갔다 (ref/.value부터 Pinia, 비동기, UI 라이브러리, localStorage까지). 이번 주에 제일 크게 배운 건 "뭘 모르는지"를 질문으로 좁혀가는 과정 자체였다.

## 사전에 공부한 내용

구현에 들어가기 전에 자바스크립트 객체, const, ref()/.value, Virtual DOM, CSR/SSR, SPA 구조, 디렉티브(v-bind/v-model/v-on) 등 12개 주제를 복습해서 [공부노트.md](./공부노트.md)에 정리했다. 노트에서 정리한 개념이 이 프로젝트에서 실제로 쓰인 곳:

- **ref()와 .value**: `weatherList`, `searchQuery`, `selectedCityInfo` 전부 ref로 선언. 스크립트 안에서는 `searchQuery.value`처럼 .value로 접근하고, 템플릿에서는 생략하는 규칙을 그대로 적용했다.
- **객체(key-value)**: `icons` 객체가 "날씨 상태 → 이모지" 짝을 담는 상자. `:class="{ active: ... }"`의 클래스 바인딩도 노트에서 정리한 그 객체 문법이다.
- **디렉티브**: v-for(카드 반복), v-if/v-else-if/v-else(온도 배지, 검색 3분기), v-bind(`:key`, `:value`, `:class`), v-on(`@click`, `@input`)을 골고루 사용.
- **v-model = v-bind + v-on**: 노트에서 "v-model은 사실 둘을 합친 것"이라고 정리했는데, 이번 과제에서는 그 합쳐진 걸 일부러 풀어서 `:value` + `@input`으로 직접 구현했다 (한글 IME 확인 목적).
- **파일 연결 흐름**: package.json → index.html → main.js → App.vue 흐름 그대로 프로젝트를 구성했고, RouterView 자리에 이 페이지(WeatherMockup.vue)가 끼워지는 구조다.
- **views 폴더**: URL 하나(/weather)에 대응하는 완전한 페이지라서 components가 아닌 views 폴더에 만들었다.

## 신경 쓴 포인트

- **한글 IME 처리**: `v-model`은 한글 조합(composition)이 끝나야 값이 반영되는데, `:value` + `@input`으로 직접 처리하면 조합 중간 글자까지 매 입력마다 갱신된다. 이 차이를 눈으로 확인하는 게 목적이라 일부러 v-model을 쓰지 않았다.
- **이벤트 버블링 차단**: [상세보기] 버튼이 카드 내부에 있어서, `.stop` 없이 클릭하면 alert 후 카드의 클릭 이벤트까지 실행돼 상태바 메시지가 바뀐다. `@click.stop`으로 버튼 클릭이 카드로 전파되지 않게 막았다.
- **watch와 watchEffect의 차이**: watch는 "무엇을 감시할지"를 명시하고 값이 바뀔 때만 실행, watchEffect는 콜백 안에서 쓴 반응형 값을 자동 추적하고 시작하자마자 1회 실행. 상황에 따라 골라 쓰는 기준을 주석에도 남겼다.
